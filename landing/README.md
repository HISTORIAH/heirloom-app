# Heirloom, Landing Site

**The page a crawler sees. Prerendered, in nine languages, with no framework in the way.**

## Why this package exists

The app is a Vite + React SPA: the server hands out an empty `<div id="root">`
and JavaScript fills it in. That is fine for a wallet-gated dashboard and bad
for a marketing page, because the first thing a search crawler receives is a
shell with no copy in it.

So the landing moved out. This package renders the same page — identical
markup, identical CSS, identical copy — to static HTML at build time. Nothing
is rebuilt in the browser, and there is no hydration step, because there is no
component tree to hydrate.

| | landing (this package) | app |
|---|---|---|
| Domain | `heirlm.xyz` | `app.heirlm.xyz` |
| Framework | Astro 5, static output | Vite + React 18 SPA |
| Rendering | Prerendered at build | Client-side |
| JS shipped | ~2.7 KB of inline islands | ~410 KB gzipped |
| Indexable | Yes — 9 locale documents | No — `noindex` throughout |

## What it produces

```
dist/
├── index.html          en   →  https://heirlm.xyz/
├── es/index.html       es   →  https://heirlm.xyz/es/
├── zh-cn/index.html    zh-CN
├── zh-tw/ ko/ ja/ pt/ vi/ tr/
├── 404.html
├── sitemap-index.xml   generated by @astrojs/sitemap, with hreflang alternates
└── robots.txt
```

Ten documents, each ~17 KB gzipped, each carrying the full ~10,000 characters
of page copy, its own `<title>`, `description`, canonical, `og:locale`, and a
`FAQPage` block generated from the same locale file the page is rendered from.
Every document links to the other nine with `hreflang`, and to `/` as
`x-default`.

## Localisation

Copy lives in `@heirloom/i18n` under the `landing` namespace
(`packages/i18n/src/locales/landing/*.ts`), split out of the app's namespace so
the two surfaces no longer share a translation file.

The app reads it through i18next at runtime. This package does not: there is no
React here, so `@heirloom/i18n/landing` exposes a plain `createLandingT(locale)`
that reads the locale object directly and falls back to English key by key. A
locale that is only partly translated still renders every string it does have.

Locale paths are lowercased BCP-47 codes (`zh-CN` → `/zh-cn/`), and English is
served unprefixed at the root. `src/pages/[locale]/index.astro` generates the
other eight from `PREFIXED_LOCALES`.

The language switcher in the footer is a list of `<a>` links rather than a
runtime language swap — which is also how a crawler discovers the other nine
documents.

## Interactivity

Three things on the page need JavaScript, and each is a plain `<script>` in the
component that owns it. There is no client framework, no `client:` directive,
and no component islands.

| Island | Where | Size |
|---|---|---|
| Mobile nav drawer | `components/nav/NavBar.astro` | 640 B |
| Demo video dialog | `components/sections/HeroSection.astro` | 655 B |
| FAQ accordion | `components/sections/FAQSection.astro` | 775 B |
| Language menu | `components/LanguageSwitcher.astro` | 415 B |
| Analytics + click tracking | `lib/analytics.ts` | 211 B (no-op when disabled) |

FAQ answers stay in the document whether an item is open or shut — they are
collapsed with `grid-rows-[0fr]`, not removed — so all eleven are indexable.

## Design system

`src/styles/global.css` is the landing's half of `app/src/index.css`, copied
verbatim: the same tokens, the same `--rule-pad` / `--page-pad` insets, the same
editorial type scale, the same mosaic grid, the same orbiting hero. The two
files share the values on purpose — the app's chrome and this page still have to
line up.

Two things differ from the React original, both because a static build knows
things a component tree does not:

- The tile entrance stagger comes from `.mosaic > *:nth-child(n) { --i }` rather
  than a render-order counter passed down through React context.
- Icons are read from `lucide-static` at build time by `components/Icon.astro`,
  pinned to the same version the app's `lucide-react` uses, so the glyphs are
  byte-identical.

## Hand-off to the app

Every call to action crosses an origin boundary now. The URLs are collected in
`src/lib/site.ts`:

| Control | Goes to |
|---|---|
| **Launch App** (nav, desktop + drawer) | `app.heirlm.xyz` |
| Nav destinations (Dashboard / Claim / Heartbeat) | `app.heirlm.xyz/<route>` |
| Hero **Launch Tour** | `app.heirlm.xyz/?tour=1` — the app reads the param and opens the product tour |
| CTA **Create Estate**, comparison "Heirloom" cell | `app.heirlm.xyz/create-vault` |

## Running it

From the repo root:

```bash
bun install
bun dev:landing       # turbo run dev --filter=landing
bun build:landing
```

Or from within `landing/`:

```bash
bun run dev           # http://localhost:4321
bun run build         # astro check && astro build → dist/
bun run preview       # serve the production build
bun run deploy        # build, then wrangler deploy
```

### Environment

Analytics is dormant unless both variables are set at build time — and because
Vite substitutes them statically, a build without them ships no PostHog at all
rather than a disabled copy of it. See `.env.example`.

```
PUBLIC_ANALYTICS_ENABLED=false
PUBLIC_POSTHOG_PROJECT_TOKEN=
PUBLIC_POSTHOG_HOST=https://us.i.posthog.com
```

Events match the app's: `$pageview`, plus a click event per hand-off
(`launch_app_nav`, `launch_tour`, `launch_app_cta`, `launch_app_comparison`,
`docs_cta`, `demo_opened`). No wallet data reaches this origin, because no
wallet does.

## Conventions

- Path alias `@/` maps to `src/`.
- One `.astro` file per section, named after the React component it replaced.
- Copy comes from `t()` — never inline a string in a section. If a section needs
  a new string, it goes in `packages/i18n/src/locales/landing/en.ts` first.
- Class strings are copied from the app rather than rewritten. When the two
  surfaces share a component's look, they should share its classes verbatim.
